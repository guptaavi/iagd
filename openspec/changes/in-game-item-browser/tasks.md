- [x] 8.2 Tell the player once, in-game, that the browser is unavailable on an unsupported renderer, and verify the message appears on `/d3d9` and not on `/d3d11` (verified from both sides: on Direct3D 9 the message was delivered on the first world load after the hook attached, and on Direct3D 11 the same code ran and said nothing. It is spoken through the same `ShowCinematicText` path the DLL already uses for "Item monitoring enabled", from two game-thread hooks that install whatever the renderer is -- the world-load hook and the stash hook. Two, because the DLL attaches to a world that is already alive, so the world-load hook cannot fire in the session that installs it, and opening the stash is when a player would go looking for the browser anyway. Only the world-load trigger was observed firing; the stash one is the same guarded call.)
- [x] 8.3 Remove the overlay's hooks in the correct detach order -- input released, overlay closed, worker stopped, hooks removed -- and verify a detach with the overlay open leaves the game running and unpatched. Verified by driving a real unload for the first time, with a remote thread, and it found two faults that reasoning had missed. First, the teardown could not run at all: it joins the search worker, and a join cannot finish inside DllMain, because the thread it waits on needs the loader lock DllMain is holding. The detach reached the input hook, restored the window procedure, and then hung for good with the renderer detour still installed. The teardown is now an exported IAGD_Unhook that runs on an ordinary thread; DllMain calls the same routine, which is idempotent, and says in the log why an unload that skipped it is about to hang. Second, EndWorkerThread never waited for the worker -- the join was commented out and replaced by Sleep(1500), with a comment acknowledging the race it left open. Survivable while the process is exiting, not survivable otherwise; it now waits, bounded, which also closes that race. With both fixed the sequence is exactly the specified one: input returned, window procedure restored, input detours removed, search worker stopped and database closed, PresentSurface detour removed, worker thread ended. Afterwards the game keeps running and is unpatched: the overlay is gone, F9 does nothing (12.9% frame change, world animation only, against the ~90% the overlay covers), and clicks move the character again (82.1%). NOT part of this task and still true: unmapping the module afterwards ends the process. The hooks are all out by then, so it is not the overlay -- OnDemandSeedInfo::Stop sets a flag and closes a _beginthread handle without waiting, and a 15-second settle did not help either, so at least one thread is still inside the image when it is unmapped. That is pre-existing lifecycle in a subsystem this change does not otherwise touch, and it is not required for a detach: nothing unloads this DLL in normal operation.
- [x] 8.4 Verify the overlay under Wine + DXVK, and disable it there with a logged reason if it does not render correctly (not verified under Wine -- there is no Wine or DXVK on this machine. Resolved as the user directed: `local.overlayEnabled` in settings.json gates the whole browser, and its default is on under Windows and off under Wine with a logged reason naming the setting.
